# SP-06: WebView2 em segundo plano (BE-05, ST-04)

| Campo | Valor |
|---|---|
| Feature | launcher-tv (Sofá) |
| Tarefa | BE-05 (spike técnico, sem o usuário, D-35) |
| Data | 2026-11-13 |
| Ambiente | Windows 11 Enterprise 10.0.22621, i7-13620H (16 núcleos lógicos), WebView2 Runtime 157.0.4341.46 (já instalado), Tauri 2.12 + `webview2-com` 0.39, build `release` no alvo `x86_64-pc-windows-gnu` (ver nota no fim) |
| Código | descartável, fora do repo (pasta de rascunho `spikes\sp06`) |
| Impacto | ADR-0001, RN-21, M-04, BE-20, BE-21, seção 6 da arquitetura (metas de memória) |

## 1. O que foi testado e como

App Tauri descartável com **300 capas sintéticas JPEG 600×900** (as 300 `<img>` ao mesmo tempo, sem virtualização: **pior caso**, ~140 KB cada, 42 MB no total) numa grade, um halo CSS animado (`opacity`/`transform`, 1,6 s) e um laço `requestAnimationFrame` contínuo. O núcleo do spike orquestra as fases e mede **a árvore inteira de processos** (o `sp06.exe` e os 6 processos `msedgewebview2.exe`; CPU por `GetProcessTimes`, memória por `K32GetProcessMemoryInfo` com `PROCESS_MEMORY_COUNTERS_EX2`):

- **A**: janela visível, 10 s.
- **B**: `window.hide()` + `ICoreWebView2Controller::put_IsVisible(false)`, sem suspender, 10 s.
- **C**: B + `ICoreWebView2_19::put_MemoryUsageTargetLevel(LOW)` + `ICoreWebView2_3::TrySuspend`, 15 s.
- **D**: 6 ciclos `Resume` + `show` + `IsVisible(true)` → tempo até o **primeiro `requestAnimationFrame` confirmado de volta ao núcleo** (comando IPC), depois ocultar e suspender de novo.
- **E**: de volta à frente depois dos ciclos, 8 s.

| A) Na frente (pior caso: 300 capas decodificadas, rAF + halo) | 4,8% a 5,9% | 0,30% a 0,37% | **293 MB** | 363 MB |
| B) Oculta, sem suspender | 0,16% a 0,31% | 0,01% a 0,02% | **127 MB** | 195 MB |
| C) Oculta + `TrySuspend` + memória `LOW` | **0,00% a 0,21%** | **0,00% a 0,013%** | **118 MB** | 192 MB |
| E) De volta à frente depois de 6 ciclos | 6,6% a 7,6% | 0,42% a 0,48% | 70 MB (provavelmente o Chromium descartou o cache de imagens decodificadas durante a suspensão; sobe quando as capas são pedidas de novo) | 192 MB |

| Medida | Resultado |
|---|---|
| Capas: `decode()` das 300 | ~540 ms depois do `setup` do Tauri (cache frio de disco não medido) |
| `TrySuspend` | concluiu em 0 a 12 ms, `IsSuspended = true` |

Variante testada: **descarregar o DOM** (esvaziar a grade) antes de suspender. A memória caiu de ~200 para ~192 MB de commit (nada relevante) e a retomada passou de ~30 ms para **~555 ms** (reconstruir e redecodificar as 300 capas). **Não compensa.**

## 3. Conclusões frente às metas

| Meta | Resultado | Veredito |
|---|---|---|
| CPU suspenso < 0,3% (RN-21, meta interna) | 0,00% a 0,21% de **um núcleo** (≤ 0,013% do total) | **Atingida** |
| Retomada < 300 ms (M-04) | **~30 ms** | **Atingida com folga** (10×) |
| Memória < 120 MB suspenso | working set privado **118 MB** (suspenso) e 127 MB (oculto); commit privado 192 MB | **No limite** (118 MB ≤ 120 MB). Em commit passa de 190 MB. A conta depende de qual número se lê; o Gerenciador de Tarefas mostra o working set privado |
| Memória < 250 MB na frente | 293 MB no pior caso (300 capas decodificadas ao mesmo tempo) | **Estourada no pior caso**; com a grade virtualizada (≤ ~60 capas montadas, arquitetura 3.4) a conta é outra. Medir de novo com a UI real (FE) |

Pontos que importam ao desenho:

1. **Ocultar já derruba quase tudo.** Com o controlador invisível, o Chromium para o rAF e as animações: a CPU cai de ~5% para ~0,2% de um núcleo mesmo sem `TrySuspend`. O `TrySuspend` leva a CPU a ~0 e reduz o working set total (611 → 374 MB contando páginas compartilhadas; 127 → 118 MB só privado). Ele é barato e confiável (≤ 12 ms) e **deve ficar**, mas o ganho principal vem de `IsVisible(false)`. **`TrySuspend` exige `IsVisible = false` antes**: a ordem do `BE-20`/`BE-21` é `hide` + `put_IsVisible(false)` + `TrySuspend`; na volta, `Resume` + `put_IsVisible(true)` + `show`.
2. **Não descarregar a UI nem navegar para `about:blank`**: a retomada passa de ~30 ms para ~555 ms sem ganho de memória que justifique.
3. **Piso de memória do WebView2**: com 6 processos `msedgewebview2.exe` mais o `sofa.exe`, o piso observado é ~190 MB de commit e ~70 a 120 MB de working set privado, **independente do conteúdo**. As metas de memória da seção 6 da arquitetura devem ser lidas como working set privado; a meta de 250 MB na frente precisa ser reconferida com a UI real e a grade virtualizada.
4. O `MemoryUsageTargetLevel = LOW` isolado deu ganho pequeno (≈ 2 a 9 MB). Manter (custo zero), sem contar com ele.
5. CPU na frente, no pior caso (rAF contínuo + halo + 300 capas montadas), foi 5 a 7,6% de um núcleo (0,3 a 0,5% do total). É uma carga de teste proposital; a UI real anima só `transform`/`opacity` do item em foco e para quando oculta.

## 4. O que não foi medido (QA-17)

| Item | Motivo |
|---|---|
| Windows 10 22H2 e Runtime do bootstrapper | Sem VM (SP-07); o comportamento de `TrySuspend` é o mesmo do runtime Evergreen, mas a versão do runtime na sala pode ser anterior |
| Retomada com um jogo em tela cheia por cima e GPU ocupada | Combina com SP-01 e QF-01; medir com o app real no BE-21 |
| CPU/memória do Sofá real durante a sessão de um jogo | BE-20 mede (meta CPU < 1%) e QF-07 confirma |

## 5. Nota de build (alvo GNU na máquina de dev)

A máquina de dev não tem MSVC Build Tools; o spike foi compilado com Rust `-gnu` (MinGW user-scope). No alvo GNU o `WebView2Loader.dll` aparece **ao lado do exe** (carregador dinâmico); no alvo MSVC (release) o carregador é estático, como pressupõe a SEC-23. Não afeta as medidas acima (a DLL é só o loader), mas o teste de DLL planta da SEC-23 só vale no build MSVC.

## 6. Impacto

- **ADR-0001 / seção 6**: escrever as metas de memória como "working set privado" e deixar a de 250 MB na frente sujeita à medição com a UI real; a de 120 MB suspenso é cumprida no limite (118 MB).
- **BE-20 / BE-21**: ordem `hide` → `IsVisible(false)` → `MemoryUsageTargetLevel(LOW)` → `TrySuspend`; retomada `Resume` → `IsVisible(true)` → `show`. Não esvaziar a UI. Meta de retomada do BE-21 (painel ≤ 3 s) não sofre com o WebView2 (~30 ms).
