| Campo | Valor |
|---|---|
| Feature | launcher-tv (Sofá) |
| Tarefa | BE-04 (spike técnico, sem o usuário, D-35) |
| Data | 2026-11-13 |
| Status da tarefa | **bloqueado: sem VM** (parcialmente executado no host) |
| Ambiente | Windows 11 Enterprise 10.0.22621; o usuário da máquina é **conta comum** (sem elevação; o registro de tarefa com `RunLevel` mais alto foi negado) |
| Código | descartável, fora do repo (pastas de rascunho `spikes\sp07`, `spikes\sp07b`) |

## 1. Por que está bloqueado (e o que foi possível)

O alvo do spike é uma **VM Windows 10 22H2 (principal) e Windows 11**, com conta padrão + credencial de outra conta administradora, NSIS instalado como administrador, Process Monitor e DLLs plantadas. Na máquina de dev:

- Não há máquina virtual utilizável: sem Windows Sandbox, sem ferramentas de gerenciamento do Hyper-V (`Get-VM` inexistente), sem ISO ou VHDX de Windows, sem VirtualBox/VMware. Habilitar Hyper-V ou o Sandbox exige administrador, e o usuário não participa dos spikes (D-35).
- Instalar o NSIS como `perMachine` e abrir o UAC exigem interação e uma credencial de administrador. O Process Monitor exige carregar driver (administrador).
- **Não foram criadas contas de usuário do Windows no host** (regra do spike): fica **uma pergunta para o usuário** (seção 6).

Mesmo assim, **o host serve para o que não depende de VM nem de UAC**, já que o usuário da máquina de dev é uma conta comum: a criação da tarefa por `ITaskService` sem administrador, o fallback, a remoção por handle sem seguir junction e o mutex da instância única. Foi feito.

## 3. Tarefa de logon por `ITaskService`, como conta comum (pergunta 1 e 2)

Teste `sp07 task`: cria `Sofa Spike07 (<SID>)` na raiz do Agendador **só com os campos do ADR-0006** (sem XML concatenado, sem `schtasks.exe`), lê de volta, executa, enumera e apaga. A tarefa de teste foi removida no fim de cada execução e a limpeza foi conferida (nenhuma tarefa `Sofa Spike07*` restante, arquivo de saída apagado).

| # | Teste | Resultado |
|---|---|---|
| T1 | `RegisterTaskDefinition(TASK_CREATE_OR_UPDATE, UserId = SID atual, TASK_LOGON_INTERACTIVE_TOKEN)` com `RunLevel = TASK_RUNLEVEL_LUA`, `LogonTrigger` com `UserId` = SID, `ExecAction` `"<exe>"` + `--autostart`, `ExecutionTimeLimit = PT0S`, `MultipleInstancesPolicy = IgnoreNew`, sem parada em bateria | **OK em 19 ms, sem UAC**, como conta comum |
| T2 | Ler de volta (`IRegisteredTask::Xml` e `IPrincipal`) | `<LogonType>InteractiveToken</LogonType>`, `<UserId>` = SID, `<ExecutionTimeLimit>PT0S`, `<MultipleInstancesPolicy>IgnoreNew`, `<Command>` entre aspas, `<Arguments>` com `--autostart`, `DisallowStartIfOnBatteries=false`, `StopIfGoingOnBatteries=false`, `LogonTrigger` presente e habilitado. **`IPrincipal.RunLevel = 0` (LUA)** |
| T5 | `LastTaskResult` antes de rodar | `0x41303` (`SCHED_S_TASK_HAS_NOT_RUN`): o BE-36 não pode tratar isso como falha |
| T7 | `IRegisteredTask::Run` e conferir o token do processo | Processo iniciado em **100 a 450 ms**; `TokenIsElevated = 0`, **integridade `0x2000` (Medium)**; `argv` recebido `["--autostart"]` |
| T3 | Enumerar a raiz por COM (13 tarefas) por prefixo `Sofa Spike07 (` e apagar por `DeleteTask` | **Viável**: achou só a tarefa de teste, apagou com sucesso. É a alternativa por COM do SEC-32 e dispensa `schtasks.exe`. Só falta ver se o NSIS consegue (no desinstalador elevado, em C++/plugin) — pendente de VM |
| T4 | `RunLevel = HIGHEST` como conta comum | **`E_ACCESSDENIED` (0x80070005)**: a conta comum não consegue criar tarefa elevada (AF-05 garantido pelo sistema) e o erro é o gatilho do fallback |
| T6 | Tarefa em nome de outro SID (SYSTEM) | **`E_ACCESSDENIED`**: não dá para criar tarefa em nome de outra conta |

Correções de redação para BE-36 (têm efeito nos testes):

1. **O XML exportado não traz `<RunLevel>` quando é LeastPrivilege** (é o valor padrão e é omitido). O teste "XML exportado com `LeastPrivilege`" do BE-36 deve verificar **a ausência de `<RunLevel>HighestAvailable</RunLevel>`** e `IPrincipal.RunLevel == TASK_RUNLEVEL_LUA`, não a presença de `LeastPrivilege`.
2. `IPrincipal.UserId` pela API **não devolve o SID literal** (devolveu outra forma de nome da conta); no XML aparece o SID. Para a regra "tarefa só é do Sofá se `UserId`, `RunLevel`, `LogonType` e `Path` baterem", comparar `UserId` por **SID** (resolver o nome pela API com `LookupAccountNameW` e comparar os SIDs) ou ler o XML.
3. O `Path` do `ExecAction` vem **entre aspas** no XML porque foi gravado com aspas; comparar normalizando as aspas.

## 4. Remoção de dados por handle, sem seguir junction (pergunta 4, SEC-31)

Algoritmo do ADR-0006 §6b, em escala de spike, rodando como conta comum numa pasta de rascunho com uma pasta-isca de 50 arquivos:

- Cada entrada é aberta com `CreateFileW(FILE_FLAG_OPEN_REPARSE_POINT | FILE_FLAG_BACKUP_SEMANTICS)`; os atributos vêm **do handle** (`FileAttributeTagInfo`); ponto de reanálise é apagado **pelo handle, sem descer**; diretório comum é percorrido; arquivo é apagado pelo handle. Apagar usa `SetFileInformationByHandle(FileDispositionInfoEx, DELETE | POSIX_SEMANTICS | IGNORE_READONLY)`, com fallback para `FileDispositionInfo`. Cada filho é conferido: o caminho final do filho (`GetFinalPathNameByHandle`) precisa estar dentro do caminho final do pai.

| Teste | Resultado |
|---|---|
| P1: junction criada dentro da pasta de dados apontando para a isca | A junction foi **removida como ponto de reanálise (1)**, sem descer; **50 de 50 arquivos da isca intactos**; pasta de dados removida (201 arquivos, 3 pastas) em 13 ms |
| P2: corrida, 15 rodadas × 3.000 arquivos, uma thread trocando `cache\covers` por uma junction para a isca enquanto o purge roda | **57 trocas conseguidas, 0 arquivos da isca perdidos** (a junção trocada foi tratada como ponto de reanálise ou nunca foi percorrida). Nenhum aborto por conferência foi necessário nesta amostra |

- `FileDispositionInfoEx` com `POSIX_SEMANTICS` funcionou nesta máquina (Win11). A tolerância ao Win10 < 1709 é o fallback já previsto.
- Limite do teste: a janela entre abrir o pai e abrir o filho é curta e 57 trocas não provam ausência de corrida. O que o teste prova é o invariante do desenho: como o ponto de reanálise é detectado **pelo handle aberto com `OPEN_REPARSE_POINT`** (e não pelo caminho), a troca por junction faz o purge apagar o link, nunca o destino. O BE-41 repete o teste com `win-integration` e mais volume.
- Não testado: `EBWebView\` com o WebView2 em uso (arquivos travados), código de saída 1 (parcial) e a chamada `RunAsUser` pelo desinstalador.

## 6. Pergunta ao usuário

**Posso criar uma conta local padrão de teste no Windows do host** (por exemplo `qa-sofa-std`, sem privilégios, removida ao fim) para testar a tarefa de logon, o autostart por conta e o desinstalador com dados de outro perfil? Criar conta exige administrador, então o usuário precisaria criá-la ou aprovar a elevação. Sem isso (e sem VM), esses itens ficam no roteiro único do QA-17.

## 7. Impacto nos ADRs e tarefas

- **ADR-0006**: a tarefa de logon do usuário comum **funciona sem administrador** e o fallback tem um gatilho real e testável (`E_ACCESSDENIED`). O mutex do plugin de instância única não tem SID (decisão de manter o plugin e ignorar `argv`). Para o desinstalador, a remoção por COM por prefixo é viável do lado do Windows; falta só a prova no NSIS.
- **BE-35**: confirmar na implementação que o callback ignora `argv`; o `AllowSetForegroundWindow` do plugin é bom para trazer a janela.
- **BE-36**: aplicar as 3 correções de teste da seção 3; tratar `LastTaskResult = 0x41303` como "ainda não rodou".
- **BE-41**: reaproveitar o algoritmo do spike (handle + `OPEN_REPARSE_POINT` + conferência do caminho final) e repetir o teste de corrida em `win-integration`.
